# Parity assessment: Ignidash vs ProjectionLab

**Date:** 2026-10-30
**Scope:** feature-parity assessment only. No implementation was proposed or performed.
**Method:** four read-only codebase scouts, one per domain, mapping the public ProjectionLab feature
matrix onto this repository's actual source. Static reading only — no tests executed, no runtime
observation. Every verdict cites `path:line`; where a scout inferred behavior rather than observing
it, that is noted in the item.

**Headline:** 4 of 46 capabilities are at full parity. 26 are partial, 16 absent.

## How to read the verdicts

| Verdict     | Meaning                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------- |
| **FULL**    | The capability exists and matches the named behavior.                                       |
| **PARTIAL** | The concept exists but a named sub-capability is missing. The gap column says exactly what. |
| **ABSENT**  | No code implements it.                                                                      |

The distribution matters more than the count. Absences cluster in the _product_ layer (milestones,
compare mode, Sankey, progress tracking, state tax) while the _math_ layer is in places ahead of
ProjectionLab. This is not an MVP with shallow math; it is deep math with a narrow product surface.

## Level-set against ProjectionLab's own phasing

ProjectionLab's published roadmap defines an MVP (accounts, income, expenses, debts, a simple
waterfall, deterministic projection, net-worth **and Sankey** charts, JSON import/export, Docker) and
a v2 (milestones, Monte Carlo plus backtesting, Roth conversions, RMDs, Social Security, compare mode).

Ignidash is approximately **MVP minus the Sankey, plus most of v2's engine work**. It has Monte Carlo,
historical backtesting and RMD mechanics. It does not have milestones, compare mode, Roth conversions,
or real Social Security estimation.

## 2. Simulation engine

**The decisive architectural fact: Ignidash runs a monthly loop, ProjectionLab runs annual with
proration.** `runSimulation` advances one month per iteration (`simulation-engine.ts:145`,
`incrementSimulationTime:200-215`), converts annual provider returns geometrically
(`returns.ts:93-103`), and settles taxes annually _inside_ the monthly loop on `month % 12 === 0`
(`simulation-engine.ts:171`). `SimulationDataPoint`s are emitted once per year (`:186-198`); no
month-level output is retained.

### Nominal/real leaks (correctness, not parity)

1. **Asset yields are nominal, applied to real balances.** `returns-provider.ts:12-14` documents
   "Nominal yield rates"; `returns.ts:64-68` and `account.ts:296-309` use them directly. Taxable
   dividend/interest income is therefore overstated by roughly ×(1+inflation).
2. **Physical-asset appreciation is not deflated** (`physical-assets.ts:392-398`) while its mortgage
   interest is — a mixed convention inside one object.
3. Charts label provider output "Real Stock/Bond/Cash Rate" (`chart-data-extractor.ts:299-302`)
   while the same provider returns nominal yields for taxation. Easy to read as "all real".

## 3. Tax engine

716 lines of implementation: `src/lib/calc/taxes.ts` (584) + `src/lib/calc/tax-data/` (132), tested by
`taxes.test.ts` (1415) and `tax-data/tax-data.test.ts` (168).

**Shape:** rules are genuine data tables (arrays of `{min,max,rate}`) — the right foundation — but
they are **single-tax-year constants** with no year dimension. `TaxProcessor` is constructed once per
simulation with only `filingStatus` (`simulation-engine.ts:117`); `simulationState.time.year` is never
read by tax code. Three `switch` statements on `FilingStatus` select the tables (`taxes.ts:526-568`).
Annual upkeep therefore means hand-editing six TS files plus hard-coded assertions
(`tax-data.test.ts:27-41,115-121`).

## Bugs found that are not parity gaps

Ordered by blast radius. All should be fixed on their own merits.

1. **`new Date()` inside the engine** — `simulation-engine.ts:291,418`, `timeline-form-schema.ts:83`.
   Start age, horizon and date labels shift daily; "reproducible with a fixed seed" is only true
   within a calendar day. Blocks compare mode and any regression baseline.
2. **Nominal yields applied to real balances** — taxable dividend/interest overstated ≈ ×(1+inflation).
3. **HSA withdrawals taxed unconditionally** while contributions are deducted — the account behaves as
   a traditional IRA.
4. **Three inconsistent "chance of success" definitions** over the same trials
   (`key-metrics-extractor.ts:73-107`, `multi-simulation-analyzer.ts:139-141`,
   `table-data-extractor.ts:672`) — headline % and per-row column can disagree.
5. **`clonePlan` drops `glidePath`** — silent data loss on clone (`plans.ts:213-227`).
6. **`selfEmployment` and `pension`** are in the income enum (`income-form-schema.ts:14`) but a
   `.refine` unconditionally rejects them (`:45-53`) and the UI renders them disabled.
7. **Payoff estimator disagreement** — `utils/payoff-estimator-utils.ts:24-50` amortizes nominally
   while the engine uses Fisher-deflated interest, so displayed and simulated payoff differ.
8. **`privacySettings.isPrivate`** is threaded through schema, validators, transformers and a hook
   (`convex/privacy_settings.ts`, `use-convex-data.ts:216-217`) with **zero consumers**.
9. **RMD age for pre-1951 birth years** — `>=1960 ? 75 : 73` maps 72-and-earlier cohorts to 73.
10. **`help/page.tsx` is unreliable in both directions** — it lists debt and physical-asset modeling as
    unimplemented (Q1 2026) although both are fully wired into the loop. Treat any capability claim
    sourced from that page as suspect.

## Ranked gaps (dependency order)

1. **Tax year dimension** (XL) — blocks indexing, legislative toggles, and any state layer.
2. **Couples / ownership** (M–L) — ripples through every schema, the engine and all UI.
3. **Engine purity + compare mode** (M) — the `new Date()` fix is a prerequisite for both.
4. **Withdrawal strategy plugins** (M) — `getWithdrawalOrder()` must become injectable.
5. **Milestones + event binding** (M–L) — needs an expression evaluator and dependency graph.
6. **State and local tax** (L–XL) — start with one state; §3 item 11.
7. **Sankey and progress tracking** (S each) — cheapest visible wins.
8. **Optimizer** (L) — only meaningful once the engine is pure and fast.

## Open questions

  per call at `simulation-engine.ts:305`, but nested account objects come from the shared inputs). Not
  traced.
- Whether RMD proceeds parked in the synthetic account are later spent by the waterfall, which would
  change the effective tax picture. Not traced beyond `portfolio.ts:390-410`.
- The worker pool's real speedup is unmeasurable from source — there are no benchmarks in the repo.
- Glide-path interaction with annual vs monthly rebalancing was not assessed.
